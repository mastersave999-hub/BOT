## 1. Method, status vocabulary, and evidence limits

Inspected the current source files `src/engine/effectResolver.ts`, `abilityEngine.ts`, `reactionEngine.ts`, `types.ts`, `multiplayer.ts`, `combatEngine.ts`, `turnEngine.ts`, `layers.ts`, `gemPayment.ts`, `deckValidator.ts`, `opening.ts`, the relevant `Playmat.tsx` transitions/callers, all 10 test files, `cards_clean.json`, `cards_raw.json`, `scripts/audit-card-effects.py`, `CARD_EFFECT_AUDIT.md`, `RULE_GAPS.md`, `RULE_CATALOG.md`, and the complete 25-page `rulebook_raw.txt`. Findings below cite the active source and test evidence, not earlier audit prose.

| Status | Meaning used in this report |
|---|---|
| **Verified** | Actual before/after Game State assertions establish the named narrow behavior. Does not imply every rule permutation is verified. |
| **Partial** | Some behavior is implemented or tested, while a material rule path/edge is absent or unverified. |
| **Implemented but unverified** | Relevant code exists, but no adequate actual Game State test was found for that rule behavior. |
| **Missing** | No engine implementation for the requirement was found in the inspected path. |
| **RULE_AMBIGUITY** | The supplied rule text does not specify a deterministic precedence/interpretation for the cited case. Not used merely because a feature is absent. |
| **Unsupported / not official** | Not defined by the supplied official Rule Book, so no official rule is inferred. |

A function name, text-pattern match, parser output, isolated numeric helper, or passing test suite alone is not enough to mark a rule **Verified**. Test evidence is specific to the scenario asserted. “Implemented but unverified” is not a claim of correct runtime behavior.

```text
   │      ├── prevention / replacement before field exit
   │      └── destruction, bounce, exile, Magic Zone and return routing
   ├── condition/target/cost preflight + all-or-nothing resolution
   │      ├── cancellation against a pending stack/action
   │      └── every printed card effect handler
   ├── event/timing queue + pending action + trigger ordering
   │      ├── Juti / Last Words / LIFE / automatic / phase triggers
   │      ├── prevention ordering and post-combat events
   │      └── React eligibility and Chain/LIFO continuation
   ├── layer model + snapshot + exact expiration events
   │      ├── continuous effects and control-aware recalculation
   │      └── combat keywords / net POWER / attack results
   └── private Deck operation + shuffle + viewer projection
          ├── search and name matching
          └── Scout / Mill / reveal-trigger sequencing

Multiplayer sync must validate/authorize the same typed commands and preserve these
invariants; serialization alone is not rules enforcement or trusted authority.
```

**Architectural prerequisites before adding handlers:** (1) a single typed, atomic action/result pipeline shared by normal abilities, React, combat and zone changes; (2) explicit owner/controller and card-instance lifecycle; (3) formal target/condition/cost/payment selection data; (4) trigger/timing queue linked to pending action and chain; (5) event-based Layer 3 snapshot and duration expiration; (6) authoritative private Deck operations and multiplayer state validation. The current typed resolver is a useful atomic subset, but adapter and callers do not yet supply complete plans.

## 8. Rule ambiguity findings

1. **RULE_AMBIGUITY — Layer 4 expiry versus post-combat transfer (p.7, p.16):** p.7 gives Unity/Backstab different explicit end points for Avatar combat versus Construct/LIFE attacks. p.16 says Layer 4 statuses move to Layer 1/2 after combat but does not explicitly state how an effect whose text itself expires “at end of combat/attack” interacts with that transfer. The engine should not infer that a temporary buff persists; obtain an official precedence clarification or implement the explicit duration as an expiration and document the reading.
2. **3+ player priority is unspecified (p.18 official wording is turn-player/opponent Duel sequence):** this is an absent official Ad-Mua rule, not evidence that a particular order is intended. Keep 3+ Reaction windows disabled; do not label community practices as Rule Book 3.2.

**Not a Rule Book contradiction:** p.5 says revealing LIFE by an ability alone does not trigger it; p.22 schedules attack-revealed LIFE effects for the owner’s next Main Phase. These describe different reveal origins and are compatible. Simultaneous Last Words on p.23 explicitly states turn player’s trigger is first and resolves later; no APNAP rule is imported.
