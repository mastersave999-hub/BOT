## 1. Method, status vocabulary, and evidence limits

Inspected the current source files `src/engine/effectResolver.ts`, `abilityEngine.ts`, `reactionEngine.ts`, `types.ts`, `multiplayer.ts`, `combatEngine.ts`, `turnEngine.ts`, `layers.ts`, `gemPayment.ts`, `deckValidator.ts`, `opening.ts`, the relevant `Playmat.tsx` transitions/callers, all current project test files, `cards_clean.json`, `cards_raw.json`, `scripts/audit-card-effects.py`, `CARD_EFFECT_AUDIT.md`, `RULE_GAPS.md`, `RULE_CATALOG.md`, and the complete 25-page `rulebook_raw.txt`. Findings below cite the active source and test evidence, not earlier audit prose.

| Status | Meaning used in this report |
|---|---|
| **Verified** | Actual before/after Game State assertions establish the named narrow behavior. Does not imply every rule permutation is verified. |
| **Partial** | Some behavior is implemented or tested, while a material rule path/edge is absent or unverified. |
| **Implemented but unverified** | Relevant code exists, but no adequate actual Game State test was found for that rule behavior. |
| **Unsupported** | No engine behavior for the requirement was found in the inspected path. |
| **Rule ambiguity** | The supplied rule text does not specify a deterministic precedence/interpretation for the cited case. Not used merely because a feature is absent. |
| **Unsupported** | No implementation is claimed; if the official Rule Book does not define an extension, no rule is inferred. |

A function name, text-pattern match, parser output, isolated numeric helper, or passing test suite alone is not enough to mark a rule **Verified**. Test evidence is specific to the scenario asserted. “Implemented but unverified” is not a claim of correct runtime behavior.

## 5. Engine dependency map

```text
Canonical Game State + typed command / result + legal zone-move transaction
   ├── ownership/controller + capacity + attachments + Token lifecycle
   │      ├── control change
   │      ├── prevention / replacement before field exit
   │      └── destruction, bounce, exile, Magic Zone and return routing
   ├── condition/target/cost preflight + all-or-nothing resolution
   │      ├── cancellation against a pending stack/action
   │      └── every printed card effect handler
   ├── event/timing queue + pending action + trigger ordering
   │      ├── Juti / Last Words / LIFE / automatic / phase triggers
   │      ├── prevention ordering and post-combat events
   │      └── React eligibility and Chain/LIFO continuation
   ├── layer model + snapshot + exact expiration events
   │      ├── continuous effects and control-aware recalculation
   │      └── combat keywords / net POWER / attack results
   └── private Deck operation + shuffle + viewer projection
          ├── search and name matching
          └── Scout / Mill / reveal-trigger sequencing

Multiplayer sync must validate/authorize the same typed commands and preserve these
invariants; serialization alone is not rules enforcement or trusted authority.
```

**Architectural prerequisites before adding handlers:** (1) a single typed, atomic action/result pipeline shared by normal abilities, React, combat and zone changes; (2) explicit owner/controller and card-instance lifecycle; (3) formal target/condition/cost/payment selection data; (4) trigger/timing queue linked to pending action and chain; (5) event-based Layer 3 snapshot and duration expiration; (6) authoritative private Deck operations and multiplayer state validation. The current typed resolver is a useful atomic subset, but adapter and callers do not yet supply complete plans.

## 11. Phase 2.2 shared infrastructure API and limitations

- **Atomic transaction — `src/engine/gameTransaction.ts:runGameTransaction`:** clones the full GameState (including nested arrays/objects/Sets), invokes the operation on the isolated draft, validates the candidate with `validateGameState`, then returns the candidate and its committed events. Rejection, throw or invariant failure returns the original state reference and structured `{ code, reason }`; events are appended only on commit. `effectResolver.ts:resolveEffectPlan` routes supported typed plans through this transaction. Draw Phase card draws and End Phase transitions in `turnEngine.ts` are transactional; player elimination moves its cards through shared zone movement in the same transaction. `abilityEngine.ts` delegates supported ability resolution to the typed resolver and no longer retains an unreachable legacy mutation implementation. Avatar exits route attached cards through shared movement events and owner Hell. This completes the Phase 2.2 transaction/movement migration scope; unimplemented rule systems listed below remain explicitly out of scope.
- **Typed event substrate — `src/engine/gameEvents.ts`:** `GameEvent` is a discriminated union with typed payloads and a required stable `eventId`. Current producers include shared zone movement, successful typed effect commits and end/start turn. Sequence numbers append deterministically; repeated IDs are ignored; failed transactions do not commit events. Hidden-source movement IDs omit card identity. Dispatch uses a fixed snapshot, blocks reentrant replay of the same event identity, and caps nested dispatch depth. It is infrastructure only: there is no persistent trigger queue or Trigger Effects implementation.
- **Future event types (declared, not yet emitted):** avatar summon, token create/destroy, magic played/resolved, attack declaration, battle end, turn start/end, effect prevented/cancelled. Declaring payloads does not mean those transition producers exist; Trigger Effects remain out of scope.
- **Zone movement — `src/engine/gameRules.ts:moveCardBetweenZones`:** request includes `actorId`, destination and optional destination player; owner/controller remain distinct. It enforces tracked instance uniqueness (including attached instances), basic destination type checks, Avatar/Construct capacities, owner-routed private destinations, and emits privacy-aware movement/Construct events. Land Magic replacement atomically routes the former shared Land to its owner's Hell. Avatar field exits route attached cards to their owners' Hell through the same validated movement/event path; attached cards leaving with a player elimination are recorded as removed from game. End Phase discard reuses the move path and routes the chosen card to owner Hell only as an application convention; p.25 does not establish this destination. The Phase 2.2 migration of supported legacy movement paths is complete. Token move-then-remove, control change, full deck shuffle/search privacy, and some zone legality remain unsupported/partial. Control Change/Search/Scout/Mill are not implemented by this infrastructure.
- **State and multiplayer checks:** `validateGameState` checks Avatar (4/6 combined), Construct constraints, duplicate IDs including attachments, and pending discard invariants. Incoming SYNC is validated for game/seat, active sender, first-turn Battle skip, hand-limit turn transitions, and revisioned pending-discard setup. `END_PHASE_DISCARD` commands bind authenticated player, current revision, command ID and selected IDs; the host applies valid commands and duplicate/stale commands are rejected. Private Deck/hand/face-down LIFE movement events omit card instance IDs. `phase22Core.test.ts` round-trips redacted full-state SYNC snapshots and restores canonical hidden identities during pending discard and active Reaction Windows. This verifies snapshot restoration, not transport-level reconnection; PeerJS host validation remains client-side, not trusted server authority.

Test evidence: `tests/gameRules.test.ts`, `tests/effectResolver.test.ts`, `tests/multiplayer.test.ts`, `tests/abilityEngine.test.ts`, and `tests/turnEngine.test.ts`. Passing test counts do not promote unsupported individual cards.

## 13. Phase 2B — Prevention, Cancellation & Continuous Effects

**Rule source reviewed:** checked-in Battle of Talingchan Rule Book Ver. 3.2 (`rulebook_raw.txt`): p.2 zone destinations; pp.11–12 Magic timing and LIFO/no interruption; p.15 cancellation semantics and Layers 0–2; pp.15–16 Layers 1–4; p.18 Rule Text (`#`) immunity and React priority; pp.9–10 protection scope; p.24 protection ordering and once-per-exit rule; p.25 LIFE damage.

- **Cancellation — Partial, tested typed scope:** unresolved pending Magic plays, activated ability continuations and chain entries can be cancelled inside a Reaction Window; cancellation is represented by `ACTION_CANCELLED`. Existing response priority/LIFO is preserved. Cancellation does not refund a consumed Magic type. Rule Text cards are protected only when explicit `ruleTextProtected` metadata is present; no card-text parser was added.
- **Magic destination ambiguity:** p.2 states Magic cards that finish resolving go to Hell; p.15 says a cancelled Magic ability's effect is cancelled and the Magic type cannot be used again, but it does not specify the physical card's destination. The engine currently routes a cancelled pending Magic/chain Magic to owner Hell as an application convention, not a verified Rule Book destination. Cancelling an Avatar/Construct ability cancels its pending continuation and does not move that source card; destruction is a separate action.
- **Prevention — Partial, tested typed scope:** `PreventionShield` supports full/partial numeric damage reduction, destruction replacement, opponent-only effect targeting prevention, finite uses and END_OF_BATTLE / END_OF_TURN / DRAW_PHASE or source-bound lifetime. ## 14. Phase 2A — Deck Operations

`src/engine/deckOperations.ts` adds reusable typed operations; this does not parse printed text or claim any catalog card works.

- **Shuffle:** Fisher–Yates using secure runtime randomness (with a `Math.random` fallback) or an explicit seed / injected source for deterministic tests. Shuffle events are transactionally committed; invalid random sources roll back.
- **Mill:** Mills `min(requested, deck size)` from the top through `moveCardBetweenZones`; all successful cards enter public Hell and receive public movement/event identities. Underflow is non-throwing. Rule Book 3.2 p.21 explicitly says a Deck count of zero is an immediate loss, so reaching zero emits `PLAYER_DECKED_OUT` and returns the loser (and Duel winner); this is not delayed until a draw failure. Ad-Mua elimination and UI terminal-state wiring are still separate work.
- **Scout:** Opens a revision-bound, authorized-viewer choice over only the top N cards. It supports explicit top/bottom placement and selected-card ordering only when the caller has confirmed that the card effect authorizes it. Without a specified destination the inspected cards are shuffled back. Unauthorized state projections and event payloads remove inspected identities.
- **Search:** Supports typed card type, color, cost range, exact/substring name, symbol, and custom predicate criteria. Unique/fixed matches may resolve immediately; ambiguous choices are held in revision-bound pending state and revalidate membership, duplicates and count. Successful and no-match searches shuffle. A no-match search emits a public false-result event, shuffles, then blocks conflicting actions until an opponent verifies it, as p.3 requires. Private result identities and success flags are redacted; public Hell movement remains visible.
- **Transactions / multiplayer:** pending Deck choice/verification locks shared zone movement, game transactions, Magic play and Reaction Window creation. `redactLifeCardsForViewer` reveals a Scout set only to its designated viewer; other viewers receive card backs and no candidate IDs. The state engine does not yet provide a complete transport/UI workflow for beginning and resolving every effect-driven Deck operation.
- **Test scope:** `tests/deckOperations.test.ts` uses synthetic Game States. No card effect is upgraded in `CARD_EFFECT_AUDIT.md`.

### Rule Book 3.2 boundaries and unresolved behavior

1. **Deck-out timing is specified:** p.21 says zero cards in Deck is a loss immediately. The conditional “wait until a draw fails” therefore does not apply to this rulebook; Mill that empties a Deck reports deck-out after the atomic mill.
2. **Scout ordering:** p.3 prohibits players from ordering the Deck. p.7 allows Scout destinations as stated by the effect (examples include bottom or shuffle), but does not grant arbitrary chosen top ordering. The API's top-order option must only be enabled by an explicit effect instruction; otherwise the default is shuffle.
3. **Search matching:** p.3 requires shuffle after a successful target move, or immediately after no target and confirmation with the opponent/Judge. It does not specify a general matching grammar, name/archetype schema, or what to do when fewer than an exact requested count match; the API rejects that exact-count operation without partial movement. No Thai text or quoted-name parser is introduced.
4. **Ad-Mua verification:** Rule Book search confirmation is written for an opponent/Judge, but does not define which verifier should act in a 3+ player game. The current core permits any listed opponent to verify; this is an app-level choice, not an official priority rule.
5. **Triggered abilities:** pp.7–8 describe “when scouted/milled” timing. Phase 2C now includes a typed event-to-trigger resolver but Deck producers and all other lifecycle producers do not automatically invoke it; card text remains unparsed.
